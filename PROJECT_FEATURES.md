1. PROJECT OVERVIEW

NIREEKSHAK is an AI-powered MPLADS (Members of Parliament Local Area Development Scheme) project lifecycle monitoring and fraud risk intelligence platform, built as a Smart India Hackathon (SIH) Phase 2 submission.

Problem Statement:
MPLADS funds (Rs 5 Cr/year per MP) lack real-time transparency, field verification, and automated fraud detection. Projects are often sanctioned without cross-checking against duplicate works, inflated costs, or suspicious contractors.

What NIREEKSHAK Does:
- Manages the complete MPLADS project lifecycle from proposal to closure.
- Automatically computes a 0-100 multi-signal risk score per project using 9 independent anomaly detectors.
- Provides a Geospatial Surveillance Map of all projects across India plotted with real GPS coordinates.
- Maintains an immutable cryptographic audit trail (SHA-256 chained hashes) for every lifecycle action.
- Enables Vigilance Officers and Auditors to queue, investigate, and resolve red-flagged projects.
- Profiles contractor entities across projects to detect cross-project fraud patterns.

Primary Users: Six roles are modelled: MP, Approving Authority (IAS), Contractor, Field Officer (PWD/Engineer), Auditor (Vigilance), and Admin.

5. AUTHENTICATION AND ROLE-BASED ACCESS CONTROL

Authentication Flow:
1. User navigates to /login.
2. Login page calls POST /api/auth/login with username and password.
3. Backend validates credentials against the users table using SHA-256 + salt hashing.
4. On success, backend returns a custom JWT-format token (HMAC-SHA256 signed, 24h expiry).
5. Token and user profile are stored in localStorage under keys nireekshak_token and nireekshak_user.
6. All subsequent API calls include Authorization: Bearer <token> via getAuthHeaders().

JWT Implementation (custom, not a library):
- Header: { "alg": "HS256", "typ": "JWT" }
- Payload: { "sub": user_id, "username", "role", "exp": Unix timestamp }
- Signature: HMAC-SHA256 using SECRET_KEY
- Secret key default: "trustus_sih2026_nireekshak_secret_key_v2" (override via JWT_SECRET_KEY env var)

Six Defined Roles:
  MP                    -> mp.demo              -> Member of Parliament, proposes projects
  APPROVING_AUTHORITY   -> authority.demo       -> IAS Officer, approves projects and awards tenders
  CONTRACTOR            -> contractor.demo      -> Vendor, records expenditure, submits progress
  FIELD_OFFICER         -> field.demo           -> PWD Engineer, verifies geo checkpoints
  AUDITOR               -> auditor.demo         -> Vigilance Officer, manages investigations
  ADMIN                 -> admin.demo           -> National Administrator, all permissions

Demo password for all accounts: Demo@123

Frontend Permission Helpers (lib/auth.ts):
  canProposeProject()       -> MP, ADMIN
  canApproveProject()       -> APPROVING_AUTHORITY, ADMIN
  canAwardTender()          -> APPROVING_AUTHORITY, ADMIN
  canAddExpenditure()       -> APPROVING_AUTHORITY, CONTRACTOR, ADMIN
  canSubmitProgress()       -> CONTRACTOR, FIELD_OFFICER, ADMIN
  canVerifyCheckpoints()    -> FIELD_OFFICER, ADMIN
  canManageInvestigation()  -> AUDITOR, ADMIN

Backend RBAC:
- require_roles(allowed_roles) FastAPI dependency factory used on all write routes.
- Returns HTTP 403 Forbidden if role is not in allowed list.

Default Session:
- If no token in localStorage, frontend defaults to ADMIN demo user profile.
- This allows browsing without login for demo purposes.
- Backend rejects write operations that require a valid token.

7. PROJECT LIFECYCLE MANAGEMENT

Lifecycle States (project_status column values):
  DRAFT -> SUBMITTED -> UNDER_REVIEW -> APPROVED -> REJECTED
  APPROVED -> TENDERING -> WORK_STARTED -> IN_PROGRESS
  IN_PROGRESS -> INSPECTION_REQUIRED -> COMPLETED -> CLOSED
  Any stage -> RED_FLAGGED -> UNDER_INVESTIGATION

Step 1: Project Proposal (MP / ADMIN)
  API: POST /api/projects/propose
  Fields: MP name, constituency, state, district, local body, work title, description,
          category, proposed amount, latitude, longitude, beneficiary info, proposed location
  Creates: Project record (status SUBMITTED, approval_status PENDING), AuditLog entry
  Also: Runs initial risk calculation via the 9-signal engine

Step 2: Digital Approval (APPROVING_AUTHORITY / ADMIN)
  API: POST /api/projects/{id}/approve
  Fields: Approving officer name, official ID badge, approval remarks
  Creates: ProjectApproval record with SHA-256 digital signature of ID scan
  Updates: project_status -> APPROVED
  Also: Writes AuditLog entry with previous/new status values, re-triggers risk engine
  UI: "Digitally Approve Project" modal on project detail page

Step 3: Tender Award (APPROVING_AUTHORITY / ADMIN)
  API: POST /api/projects/{id}/tender
  Fields: Contractor name, contractor registration number, awarded amount
  Creates: Tender record, creates or links ContractorRiskProfile (normalized entity name)
  Updates: project_status -> TENDERING
  Also: Writes AuditLog entry, re-triggers risk engine (contractor risk signal now active)
  UI: "Award Tender and Work Order" modal on project detail page

Step 4: Record Expenditure (APPROVING_AUTHORITY / CONTRACTOR / ADMIN)
  API: POST /api/projects/{id}/expenditure
  Fields: Expense category (Civil Materials / Labor and Wages / Heavy Equipment /
          Electrical and Plumbing / Consultancy Milestone), description, amount
  Creates: ExpenditureTransaction record with cumulative total, auto-set entered_by and timestamp
  Updates: project.expenditure_amount (running total)
  Also: Writes AuditLog entry, re-triggers full risk engine
  UI: "Append Expenditure Transaction" modal on project detail page

Step 5: Submit Progress Update (CONTRACTOR / FIELD_OFFICER / ADMIN)
  API: POST /api/projects/{id}/progress
  Fields: Physical completion percentage (0-100), work description
  Creates: ProgressUpdate record
  Computes: financial_progress_percent = cumulative_expenditure / awarded_amount * 100 (auto)
  Updates: project_status -> IN_PROGRESS
  Also: Writes AuditLog entry, re-triggers risk engine (progress mismatch signal now active)
  UI: "Submit Milestone Progress" modal on project detail page
  NOTE: Modal shows "Field Photo Automatically Geo-Tagged" - actual photo capture and GPS
        geo-tagging in browser is NOT implemented. This is a UI label only.

Step 6: Geo Checkpoint Verification (FIELD_OFFICER / ADMIN)
  API: POST /api/projects/{id}/checkpoints/{cp_id}/verify
  Verifies: submitted GPS coordinates vs expected coordinates using Haversine distance
  Threshold: allowed_radius_meters (default 150m)
  Updates: verification_status -> VERIFIED or MISMATCH
  Also: Writes AuditLog entry, re-triggers risk engine
  UI: Tab 7 (Geo Checkpoints) on project detail page

Automatic Investigation Triggering:
  Triggered when trigger_risk_recalculation() computes risk_score >= 80 (RED_FLAG level):
  - InvestigationCase created automatically (if not already exists for this project)
  - project_status updated to UNDER_INVESTIGATION
  - contractor.suspicious_projects count incremented (idempotent - only once per project)
  - Notification record created with severity CRITICAL

9. RISK INTELLIGENCE ENGINE - NINE ANOMALY DETECTORS

Location: NIREEKSHAK-datasets/apps/api/services/risk_engine/
Orchestrator: risk_fusion.py -> calculate_fused_risk()

Trigger: Automatically called on every lifecycle mutation (proposal, approval, tender,
         expenditure, progress update, checkpoint verification).

Nature: Deterministic, rule-based system.
        scikit-learn and pandas are in requirements.txt but no ML model inference
        was found in the active scoring pipeline.

Scoring Architecture:
Each of the 9 detectors independently returns:
  - flagged: bool
  - signal: dict with type, title, severity, scoreImpact, description
  - score: int (detector-local score)

Fusion Function (risk_fusion.py):
  1. Sums all scoreImpact values from flagged signals.
  2. If 3 or more signals active: applies 1.15x compound multiplier.
  3. Clamps final score to 0-100.
  4. Classifies: 0-29 = LOW, 30-59 = MEDIUM, 60-79 = HIGH, 80-100 = RED_FLAG.
  5. Generates deterministic summary_text string.
  
Confidence score: 0.91 if >= 2 signals active, else 0.85.

DETECTOR 1: Cost Anomaly (cost_anomaly.py)
  Compares project cost against peer projects using IQR statistical bounds.
  Inputs: project cost, peer median, peer IQR low/high
  Default peer values: median Rs 25,00,000; IQR low Rs 15,00,000; IQR high Rs 35,00,000
  upper_whisker = IQR_high + 1.5 x IQR
  extreme_whisker = IQR_high + 3.0 x IQR
  Flags if cost > 1.2x peer median  -> MEDIUM, +8 pts
  Flags if cost > 1.4x peer median  -> HIGH, +16 pts
  Flags if cost >= 2.0x peer median -> CRITICAL, +24 pts

DETECTOR 2: Progress vs Expenditure Mismatch (progress_anomaly.py)
  Detects divergence between reported physical completion and financial drawdowns.
  Inputs: physical_progress_percent, financial_progress_percent
  discrepancy = financial_progress - physical_progress
  Flags if discrepancy >= 15% -> MEDIUM, +8 pts
  Flags if discrepancy >= 25% -> HIGH, +15 pts
  Flags if discrepancy >= 40% -> CRITICAL, +22 pts

DETECTOR 3: Expenditure Velocity (expenditure_velocity.py)
  Detects abnormally rapid fund consumption relative to physical execution.
  Inputs: list of ExpenditureTransaction records, allocated_amount, physical_progress
  burn_rate = total_spent / allocated_amount
  Flags if burn_rate >= 0.50 and progress < 20% -> HIGH, +15 pts
  Flags if burn_rate >= 0.70 and progress < 35% -> CRITICAL, +20 pts

DETECTOR 4: Cost Overrun (cost_overrun.py)
  Flags when actual expenditure significantly exceeds the awarded contract amount.
  Module confirmed to exist and is imported by the fusion engine.
  Specific thresholds were not re-verified in this inspection session.

DETECTOR 5: Tender Anomaly (tender_anomaly.py)
  Evaluates abnormal deviations between engineering estimate and awarded tender.
  Inputs: estimated_amount, tender_amount, awarded_amount
  deviation_percent = (awarded - estimated) / estimated x 100
  Flags if deviation >= +25%  -> Inflated Tender Award, HIGH, +16 pts
  Flags if deviation <= -30%  -> Aggressive Underbidding, MEDIUM, +12 pts

DETECTOR 6: Duplicate Work Detection (duplicate_detection.py)
  Checks if a project is semantically or geographically similar to existing registered works.
  Inputs: project description, GPS coordinates, list of peer projects
  Method: Jaccard similarity on word tokens
  Jaccard = |intersection| / |union| of word token sets
  Flags if Jaccard >= 0.70 (text match alone): +18 pts, CRITICAL if >= 80%, HIGH otherwise
  Flags if Jaccard >= 0.45 AND spatial distance <= 300m: combined flag
  Distance: Haversine formula (Earth radius = 6,371,000m)

DETECTOR 7: Geographic / Geofence Anomaly (geographic_anomaly.py)
  Three sub-checks:
  1. Project boundary: If submitted field GPS > 1,000m from registered project coords
     -> +20 pts (CRITICAL if > 5km)
  2. EXIF vs device GPS: If image EXIF GPS differs from device GPS by > 500m
     -> +15 pts (possible photo tampering)
  3. Checkpoint failure ratio: If any checkpoints have verification_status MISMATCH
     -> +12 pts scaled by failure fraction

DETECTOR 8: Timeline Anomaly (timeline_anomaly.py)
  Detects delayed, stalled, or overdue projects.
  Flags if: today > expected_completion_date AND physical_progress < 95%
    - 60 to 180 days overdue  -> MEDIUM, +10 pts
    - > 180 days overdue      -> HIGH, +15 pts
  Flags if: project status = STALLED -> HIGH, +12 pts

DETECTOR 9: Contractor Entity Risk (contractor_risk.py)
  Evaluates contractor cross-project fraud history.
  Inputs: suspicious_projects, red_flagged_projects, delayed_projects, total_projects, contractor_name
  normalize_entity_name(): strips business suffixes (PVT LTD, LIMITED, INFRA, BUILDERS, etc.)
    and uppercases to detect name variants of the same entity.
  Flags if: total bad history (suspicious + red_flagged) >= 1 -> HIGH, +14 pts
  Flags if: total bad history >= 3                            -> CRITICAL, +20 pts
  Flags if: delay rate >= 40% of total projects               -> MEDIUM, +8 pts

13. DIGITAL AUDIT TRAIL

Route: /audit-logs
File: apps/web/app/audit-logs/page.tsx
Backend API: GET /api/audit-logs?limit=100

Cryptographic Hash Chain:
Each AuditLog entry includes:
  - event_id: Unique ID (format: AUD-{hex})
  - event_hash: SHA-256 of "{event_id}:{user_name}:{action}:{project_id}:{previous_hash}:{timestamp}"
  - previous_hash: SHA-256 hash of the immediately preceding audit event.
    The genesis event uses 64 zeros as its previous_hash.

This structure creates a tamper-evident blockchain-like chain. Any modification to a
historical event invalidates its hash and breaks the chain from that point forward.

Filter Controls:
  - Full-text search: by user name, action, or project ID
  - Action filter dropdown: All / Proposals / Approvals / Tender Awards / Expenditures /
    Progress Updates / Risk Flags / Investigations

Audit Log Table Columns:
  - Timestamp (ISO format, monospace)
  - User (actor full name)
  - Role
  - Action (e.g., PROJECT_APPROVED, TENDER_AWARDED, EXPENDITURE_RECORDED)

21. SECURITY IMPLEMENTATION

Password Hashing:
  SHA-256 with prepended salt: SHA256("sih_nireekshak_salt_" + password)
  Fallback: accepts plain SHA-256 and demo passwords (Demo@123, password123, demo123, trustus2026)
  NOTE: For production, bcrypt or Argon2 recommended. Current implementation is for demo context.

Token Security:
  HMAC-SHA256 with SECRET_KEY (default: "trustus_sih2026_nireekshak_secret_key_v2")
  24-hour expiry encoded in payload exp field
  Token verified on every protected endpoint

Audit Integrity:
  SHA-256 chained hash per audit event
  Any modification to a historical event invalidates its hash and breaks the chain

CORS:
  Backend: allow_origins=["*"] (all origins allowed)
  Appropriate for hackathon demo. Would be restricted in production.

Photo Hash Integrity:
  GeoEvidence.file_hash stores SHA-256 of uploaded photos
  GeoCheckpoint.photo_hash stores the same
  Actual hash computation location (client-side or server-side) could not be fully verified
  from the inspected routes.

25. KNOWN LIMITATIONS AND NOTES

1. Photo Geo-Tagging:
   The progress update modal displays "Field Photo Automatically Geo-Tagged with Browser Device
   Coordinates" but actual camera access, photo capture, and GPS geo-tagging via the browser
   Geolocation API is not implemented in the current codebase. This is a UI label only.

2. EXIF Metadata Extraction:
   The GeoEvidence table has exif_latitude and exif_longitude columns and the geographic anomaly
   detector uses them. However, the code that actually extracts EXIF data from uploaded photos
   was not found in the inspected routes.

3. Monthly Analytics Approximation:
   The monthly_projects data returned by /api/analytics/overview is computed as fixed proportional
   fractions of total_projects (August = 100% of total) rather than actual per-month created_at
   date groupings from the database.

4. CORS is Open:
   The backend allows all origins (allow_origins=["*"]). Appropriate for hackathon demonstration
   but would need to be restricted in a production deployment.

5. Secret Key in Code:
   The JWT SECRET_KEY has a hardcoded default value. It should be set via the JWT_SECRET_KEY
   environment variable for any real deployment.

6. Notification Delivery:
   The Notification table is populated when high-risk projects are flagged, but there is no
   email, SMS, or push notification delivery mechanism implemented.

7. No File Storage:
   Photo references in GeoEvidence, GeoCheckpoint, ProjectApproval, and ProgressUpdate are
   stored as URL strings. There is no S3, file server, or local file storage implementation
   in the codebase.

8. Report Export:
   The Reports page renders filtered project data as a table in the browser. There is no
   server-side or client-side export to PDF, Excel, or CSV.

9. scikit-learn Presence:
   scikit-learn, pandas, pyarrow, and joblib are listed in requirements.txt. These may have
   been used during data preparation/seeding or for an earlier ML prototype, but no trained
   model inference was found in the active risk-scoring pipeline.

10. Single-Source Cost Anomaly:
    The cost anomaly detector uses hardcoded default peer statistics (median Rs 25L,
    IQR Rs 15L to Rs 35L) when no peer data is provided. The accuracy of the peer comparison
    depends on the seeded dataset and whether peer project data is passed from the lifecycle route.
